Options execution engine for a live derivatives platform

Seventeen Python processes that watch every open option leg tick by tick, fire and protect real broker orders, and guarantee that a position is never exited twice — or left orphaned when a worker dies mid-order.

The problem

A multi-leg options strategy has to be scheduled, priced, fired, then watched continuously against stop-loss, take-profit, trailing and break-even triggers. Several independent workers can detect the same breach on the same tick. If two of them act, the platform exits a position twice and takes an unintended opposite trade. If the process dies between calling the broker and recording the order id, a live position exists that the engine cannot see.

What I built

Every cross-worker state change is a server-side Redis Lua script, so the check-and-claim happens inside one atomic execution — no distributed lock, no read-modify-write window. Exit claiming, partial exits and order fencing all use the same pattern, with four fencing tokens verified before any order can fire, so a stale scheduler dispatch physically cannot double-fire a strategy. A dedicated reconciliation worker sweeps every 30 seconds for legs that were fired but never recorded, probes the broker's order book, and re-attaches what it finds rather than assuming nothing happened.

The performance work

The per-tick risk check was the bottleneck, so I flattened the entire active leg set into contiguous NumPy arrays and rewrote the loop in Cython — typed memoryviews, bounds checking off, zero Python dict lookups and zero heap allocation inside the tick. Hot-path event logging goes through a lock-free ring buffer of fixed 80-byte numeric slots, so no Python object is ever constructed on the fast path. Both extensions import behind a fallback: an unbuilt binary costs speed, never correctness.

Result

A fleet defined by a single manifest that also generates the start/stop scripts and the container's exposed ports — with a test that fails the build if those copies ever drift. 1,856 tests run green in 55 seconds, backed by dead-letter queues on eight pipelines, 79 Prometheus metrics, per-worker health endpoints and a chaos-drill directory for killing workers on purpose.

Real-time P&L, position and margin streaming gateway

One authenticated connection that multiplexes live trade events, per-strategy and portfolio P&L, broker books and SPAN margin into the browser — and survives network drops without ever showing a client stale, duplicated or missing data.

The problem

Streaming live data is easy. Streaming it correctly is not. Redis trims its streams, so a client that reconnects after a gap can silently miss events it will never learn about. Resolving the live cursor at read time loses everything published during the reconnect window. And a single malformed field written by an upstream service is, to naive error handling, indistinguishable from Redis being down — which tore down the shared connection pool once per second for every logged-in user.

What I built

The live cursor is pinned once to a concrete stream id before the read loop starts, so nothing published mid-reconnect is lost. A client-supplied resume id is sanitised and compared against the oldest retained entry, so a genuine trimmed gap forces a clean re-bootstrap instead of a silent hole. Error handling separates connection failures from data-parse failures, and connection invalidation is a compare-and-swap so one transient blip can't cascade into a reconnect storm across every user.

The judgement call

A wrong margin number is worse than no margin number. When an open leg can't be parsed into a position, the gateway refuses the whole envelope and logs a warning rather than emitting a figure that understates a trader's risk. Because the gateway is strictly read-only over engine-owned keys, intra-day margin peaks are held on a per-connection monotonic floor — stored with the timestamp they were emitted with — so a peak never visibly regresses.

Result

7,868 lines of source against 6,474 lines of tests — a 0.82 : 1 ratio — with 278 tests green in under nine seconds and no live infrastructure required. Four quality gates run on every change: ruff, mypy in strict mode, pytest, and an import-linter contract that makes violating the hexagonal layering a build failure rather than a code-review argument.

Exchange-accurate SPAN + ELM margin engine

Portfolio margin computed from the exchanges' own daily risk files, so the capital the platform blocks matches what a real broker would block — including catching a sign convention that the widely-copied public implementation gets backwards.

The problem

Approximating margin is how a platform ends up over-committing a client's capital or under-reserving against a position it can't cover. Real SPAN means parsing the exchange's published risk arrays directly. Those files refresh several times a day, and a reader that catches a rebuild half-finished will price a portfolio against a mix of old and new scenarios.

What I built

A versioned keyspace where each publish writes to fresh keys and only then flips a pointer atomically, keeping the previous version alive on a grace TTL while readers pin a version for the life of a request. NSE and BSE get fully independent pointers, so one exchange's rebuild can never tear the other. Contracts are stored as 68-byte packed structs and strikes are keyed as integers to eliminate floating-point drift.

The correctness catch

Scanning risk is max(0, max(scenario_loss)) — positive values in the exchange file are losses. The commonly copied form, max(0, −min(…)), picks the opposite position's tail and silently mis-margins the portfolio. On top of that sit the SEBI ELM rate buckets and a portfolio-versus-standalone comparison that exposes the actual spread benefit.

The performance work

Per-miss Redis round-trips dominated a margin sweep across a full option chain, so the first touch of a symbol now pulls its entire hash in a single call and keeps the raw blobs in memory — every later lookup, hit or miss, is a pure dict probe with zero round-trips. It's thread-safe without locks by capturing the immutable snapshot once per call, so a version flip can only ever poison a snapshot that has already been discarded.

Always behind a fallback, so a build problem never becomes a correctness problem.

Best fit — a job that used to finish in time and no longer does

How I work

I write tests at roughly the same volume as source, because on the systems I work on a regression isn't a bad user experience — it's an unintended trade. My streaming gateway carries 6,474 lines of tests against 7,868 lines of source, and the whole suite runs in under nine seconds with no live infrastructure, so there's never an excuse to skip it.

I prefer making invalid states impossible over documenting them. A layering rule enforced by a linter contract is worth more than a wiki page; a manifest that generates the deploy scripts and fails the build when they drift is worth more than a checklist.

And I'd rather emit nothing than emit a number I can't stand behind. That principle is literally in the margin code: unparseable positions refuse the whole response instead of quietly understating risk.
